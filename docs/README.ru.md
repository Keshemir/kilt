# kilt

Доступ по SSH к одному проекту в docker compose, а не ко всему серверу.

*Кілт* по-казахски значит «ключ». [English version](../README.md)

## Зачем

У вас один сервер. На нём магазин, блог и API, каждый в своём docker compose. Новому разработчику нужно читать логи магазина. Подрядчику на неделю нужно перезапускать API.

Обычно выбор плохой. Либо дать root, и человек увидит всё. Либо вручную настраивать пользователей, группы, ACL, правила sudo и фаервол, и где-нибудь ошибиться.

kilt делает это за вас. Открываете на сервере меню, выбираете человека, проект и уровень доступа. Всё.

```
Доступ к серверу 203.0.113.10
> ➕ Добавить человека
  alice                   весь сервер, root   SHA256:Xp3kQ9vT2mLa…
  bob                     shop (root на проект), blog (чтение)
  carol                   без проектов
  ── не через это меню ──
  · deploy: отдельная учётка, группа docker — то же, что root, ключей 1
  Выход
```

kilt — это один файл на Python без зависимостей. Меню рисует [gum](https://github.com/charmbracelet/gum), язык — русский или английский.

## Быстрый старт

Нужны Debian или Ubuntu с systemd, Python 3.9 или новее и docker compose v2.

```bash
apt install -y sudo gum nftables
install -m 755 kilt.py /usr/local/bin/kilt
kilt setup
kilt
```

`gum` есть в Debian 13 и новее. На более старых системах поставьте его [по инструкции gum](https://github.com/charmbracelet/gum#installation).

kilt работает от root и меняет настройки sshd, пользователей и правила фаервола. Прочитайте код перед установкой и сначала попробуйте на тестовом сервере. `kilt --version` покажет версию, а `kilt uninstall` уберёт kilt обратно (см. [Как убрать kilt](#как-убрать-kilt)).

## Что видит человек

У Боба «чтение» на блог и «root на проект» на магазин. Он заходит со своим ключом:

```
$ ssh bob@server
bob@server:~$ ls
blog  shop
bob@server:~$ cd shop
bob@server:~/shop$ kilt ps                 # контейнеры магазина
bob@server:~/shop$ kilt logs -f web        # логи в реальном времени
bob@server:~/shop$ kilt restart web        # нужен «root на проект»
bob@server:~/shop$ kilt exec web sh        # нужен «root на проект»
```

Чужие проекты он не видит, `docker` и `sudo` ему недоступны, до баз других проектов он не дотянется.

## Уровни доступа

Root заходит как `root@server` и может всё. Остальные заходят под своим логином. Человек без проектов может только осмотреться: процессы, диск, нагрузка. Человеку с проектами на каждый проект дают «чтение» или «root на проект».

|  | без проектов | чтение | root на проект |
|---|---|---|---|
| Читать файлы проекта | — | ✓ | ✓ |
| Читать секреты (`.env`, ключи, токены, `.git/config`, `secrets/`) | — | — | ✓ |
| Менять файлы проекта | — | — | ✓ (можно выключить) |
| `kilt ps`, `kilt logs` | — | ✓ | ✓ |
| `kilt restart`, `stop`, `start`, `exec` | — | — | ✓ |
| Подключаться к базе, Redis и веб-портам проекта | — | — | ✓ |
| Подключаться к чужим проектам, внутренним сетям, метаданным облака | — | — | — |
| Интернет (git, curl) | ✓ | ✓ | ✓ |
| Слушать порты, cron, `at`, `docker`, `sudo` | — | — | — |

Каждому человеку можно до 256 процессов, 1 ГБ памяти и одно ядро процессора, файлы — до 4 ГБ.

## Меню

Запустите `kilt` от root. Чтобы добавить человека, выберите вид доступа, введите логин, отметьте проекты и вставьте его публичный ключ (`ssh-ed25519 AAAA…`). Enter на человеке — сменить уровень, дать или забрать проект, заменить ключ или удалить. Когда доступ меняют или забирают, все процессы человека сразу завершаются.

Меню бережёт от ошибок. Чтобы выдать полный root, нужно ввести случайное число с экрана. В опасных вопросах по умолчанию выбрана «Отмена». Последний ключ root удалить нельзя. Приватный ключ, слабый RSA и уже заведённый ключ меню не примет.

## Настройки

`kilt setup` создаёт `/etc/kilt/config.json` ([пример](../examples/config.json)):

```json
{
  "host": "203.0.113.10",
  "closed": ["/opt", "/srv"],
  "service_keys": [],
  "language": "ru"
}
```

- `host` — адрес в подсказке «Пусть заходит так: ssh …». Если пусто, kilt берёт первый адрес из `hostname -I`.
- `closed` — папки, где лежат проекты. Напрямую людям эти папки закрыты. До проекта они добираются только через `~/<проект>` — ссылку на ту же папку, примонтированную ещё раз с `nosuid,nodev`. Изменения там настоящие. Системные папки, `/home` и `/var` сюда указывать нельзя.
- `service_keys` — комментарии ключей root, которые меню не показывает и не трогает, например ключ CI.
- `language` — `ru` или `en`. Если пусто, kilt берёт язык системы.

Проекты kilt находит сам по меткам docker compose. Проект сохраняет своё имя из compose, если оно короткое и простое: строчные латинские буквы, цифры и `-`, не длиннее 24 символов. Иначе kilt чистит имя и добавляет 5 символов его хеша: например, `shop_v2` станет `shop-v2-1a2b3`. Имя зависит только от имени в compose, поэтому не меняется, когда контейнеры пересоздают. Если нужно переименовать проект, указать другую папку или скрыть файлы, добавьте `/etc/kilt/projects.json` ([пример](../examples/projects.json)):

```json
{
  "shop": {"compose": "shop-prod", "dir": "/srv/shop", "hide": ["notes-with-passwords.md"]},
  "site": {"compose": "site", "dir": "/opt/site", "files": "ro"}
}
```

Ключ (`shop`) — это имя, которое люди видят в меню и в `~/shop`. `hide` закрывает от «чтения» дополнительные файлы. `exclude` — папки, которые kilt не обходит вообще, например большие папки с данными: `"exclude": ["data", "uploads/cache"]`. Прав от kilt там нет, действуют обычные права Linux. Спрятать файлы так не получится, для этого есть `hide`. `"files": "ro"` запрещает «root на проект» менять файлы — пригодится для папок, из которых выкладывает CI. Папка проекта должна лежать внутри одной из `closed`.

Оба файла должны принадлежать root, писать в них может только root. Если в файле ошибка, kilt остановится и скажет, а не будет угадывать.

## Как это устроено

kilt пользуется обычными средствами Linux и не держит своего демона.

Ключи root остаются в `/root/.ssh/authorized_keys`, над каждым — строка `#ИМЯ`. Перед каждой правкой kilt кладёт копию в `/root/.ssh/kilt-backups/`. Строки, которые он не понимает, остаются как были.

Каждый остальной человек — пользователь Linux в группе `kilt` с номером от 70000 до 79999. Номера не выдаются повторно, так что новому человеку не достанутся файлы прежнего. Ключи лежат в `/etc/kilt/keys/` и принадлежат root: второй ключ себе не допишешь.

У каждого проекта две группы: `p-<проект>` для чтения и `p-<проект>-rw` для «root на проект». Права на файлы kilt ставит через POSIX ACL. Каждый файл он открывает один раз и меняет уже открытый, поэтому подменить папку ссылкой посреди работы не выйдет. Новые файлы закрыты для «чтения» до ближайшей синхронизации, секреты закрыты всегда.

Файлы и папки, которые может открыть только владелец (права `600` или `700`, например `acme.json`, ключи SSH или папка базы данных), kilt не трогает совсем: программы, которые проверяют эти права, продолжают работать. Личным учёткам такие файлы не открыть, даже с «root на проект». В `node_modules`, `.venv`, `venv`, `vendor` и `site-packages` kilt не заходит: права получает сама папка, а файлы внутри остаются с обычными правами Linux.

По настоящему пути проекта люди не ходят. Они работают в `/run/kilt/view/<проект>/m` — втором монтировании папки с `nosuid,nodev`. Программа с setuid или файл-устройство, созданные в контейнере, там не сработают.

`kilt ps`, `kilt logs` и остальные команды контейнеров идут через правило sudo. kilt проверяет группы человека и запускает `docker` только для его проекта. `docker compose up`, `pull`, `run` и `cp` запрещены.

Сеть ограничена правилами nftables на номера 70000–79999. До самого сервера, внутренних сетей и метаданных облака люди не дотянутся. Открыты DNS-серверы из `/etc/resolv.conf`, интернет и сервисы проектов, где у человека «root на проект».

Если полные правила собрать не получилось (например, docker не отвечает), kilt ставит базовый набор, который только запрещает: сам сервер, внутренние сети, метаданные облака, `64:ff9b::/96`. DNS и интернет остаются. Полные правила закрывают ещё и IPv6-сети docker.

systemd ограничивает память, процессы и процессор и не даёт слушать порты. cron и `at` этим пользователям отключены. Их строки kilt убирает из `/etc/subuid` и `/etc/subgid`, чтобы через user namespace нельзя было сбросить группу `kilt`. В SSH разрешён только проброс `-L`: никаких `-R`, агента, X11, паролей, сертификатов и `AuthorizedKeysCommand`. Если `sshd_config` подключает `/etc/ssh/sshd_config.d/*.conf` (в Debian и Ubuntu подключает), kilt пишет свои настройки в `/etc/ssh/sshd_config.d/00-kilt.conf`. Иначе добавляет размеченный блок в конец `sshd_config`. В обоих случаях результат сначала проверяет `sshd -t`.

Когда у человека забирают проект или меняют «root на проект» на «чтение», kilt завершает его процессы и снимает биты setuid и setgid с его файлов в домашней папке, `/tmp`, `/var/tmp` и `/dev/shm`. Иначе копия `bash` с группой проекта сохранила бы ему прежний доступ.

Раз в 10 минут таймер запускает `kilt sync` и обновляет права, ключи и сетевые правила. Служба `kilt-boot` при загрузке сервера, ещё до sshd, ставит базовые сетевые правила и монтирует папки проектов. Ей не нужны ни docker, ни файлы настроек. Она же срабатывает снова, когда перезапускают или перечитывают `nftables.service`: обычный `/etc/nftables.conf` начинается с `flush ruleset`. Полные правила приходят со следующей синхронизацией, примерно через 2 минуты после загрузки. Всё, что делает kilt, пишется в `/var/log/kilt.log`, который читает только root. `kilt setup` добавляет `/etc/logrotate.d/kilt`, так что журнал раз в неделю ротируется.

У каждой команды, которую запускает kilt, есть ограничение по времени. Если в это же время кто-то другой меняет доступ, kilt ждёт до минуты, а потом говорит, что занят.

## Что стоит знать

- **«Root на проект» — это доверие.** Человек становится root внутри контейнеров проекта. Умелый может через это получить root на сервере, особенно если контейнер подключает `docker.sock`, работает в privileged или делит папку без `nosuid` или `nodev`. Такие случаи kilt записывает в журнал.
- Секреты kilt узнаёт по имени файла. Пароль внутри `config.yml` «чтение» увидит, такие файлы добавьте в `hide`.
- Новые файлы открываются для чтения только после синхронизации, до 10 минут. Так задумано.
- Если контейнеры пересоздали не через kilt, адрес контейнера до синхронизации может достаться другому проекту.
- Место на диске не ограничено.
- Запрет слушать порты требует systemd, собранного с BPF. В Debian он есть. Если на вашем сервере его нет, люди смогут открывать порты выше 1024, и `kilt setup` об этом предупредит.
- Пользователей, заведённых не через kilt, меню показывает, но не меняет. Тех, кто в `sudo`, `docker`, `wheel`, `admin`, `lxd`, `libvirt` или `disk`, меню помечает «то же, что root».
- Убрали ключ root — ещё не значит, что человек ушёл. Он мог оставить себе другой вход.
- Если `AllowUsers` или `AllowGroups` в sshd не пускают группу `kilt`, личные учётки не войдут. `kilt setup` об этом предупредит, но настройки sshd не тронет.
- Процессы, которые человек запустил внутри контейнера через `kilt exec`, продолжают работать после того, как его удалили. Если нужно быть уверенным, перезапустите контейнер.
- В `/proc` люди видят процессы других пользователей вместе с командной строкой. Не передавайте пароли в командной строке.
- Командной строки для скриптов и автоматизации пока нет: людей и их доступ меняют только в меню. Она в планах.

Подробнее — в [SECURITY.md](../.github/SECURITY.md).

## Как убрать kilt

```bash
kilt uninstall                  # откажется, пока есть личные учётки
kilt uninstall --remove-users   # сначала удалит личные учётки
```

Команда попросит ввести `yes` (или добавьте `--yes`). Потом она убирает службы kilt, таблицу фаервола, монтирования папок проектов в `/run/kilt`, записи kilt в правах на файлы проектов, группы `kilt` и `p-*`, правило sudo, ограничения, файлы sysctl и logrotate и настройки sshd. В конце пишет, что убрала. Ключи root в `/root/.ssh/authorized_keys` остаются как были. `/etc/kilt` и `/var/log/kilt.log` тоже остаются, если не добавить `--purge`. Файл `/usr/local/bin/kilt` удалите сами.

## Тесты

`tests/security.py` ставит kilt, поднимает два тестовых проекта и трёх людей и пробует взломать: через сеть, файлы, контейнеры, права, файлы с setgid, user namespace, порты, ключи и плохие команды. Ещё он проверяет загрузку без docker, перезапуск nftables, а в конце убирает kilt через `kilt uninstall`. GitHub Actions гоняет его на каждый push, с меню на русском и на английском.

Он многое меняет на машине, поэтому запускайте его только там, где не жалко. Если у вас есть Docker:

```bash
./tests/run.sh ru     # меню на русском
./tests/run.sh        # на английском
```

`tests/translations.py` проверяет, что у каждой строки меню есть английский вариант.
